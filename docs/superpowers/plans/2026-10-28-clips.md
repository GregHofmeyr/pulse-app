# Clips (phase 1: trim and share): implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a `clips` channel kind where people drop a game replay into Pulse on Windows, cut it in a local editor,
and post it in seconds plus the upload. Clips are kept forever on R2, play in a list or a 3-across wall, and can be
filtered by game and person. Replies go in the replies side panel, and reactions work as normal.

**Architecture:** a clip is a `messages` row plus a `clips` row. Its video is a `media` row whose location is
`r2`, which is the media store's R2 location, built in this push. Its thumbnail is an ordinary disk media row. The
server never handles the video bytes. It issues a signed upload URL against an upload ticket. The Tauri core
encodes with the bundled ffmpeg and uploads straight to R2 with progress. The server then confirms the object's
size with a signed HEAD and posts the clip. Playback asks the server for a fresh, short-lived signed GET each time.
Replies reuse the quotes threads, which are generalised from "a quote" to "a thread root". The editor's cut model,
presets and feed state are pure TypeScript, and ffmpeg command building is pure Rust. Both are unit-tested without
ffmpeg or R2.

**Tech Stack:** Rust (axum, sqlx/SQLite, `rusty-s3` presigning, reqwest), ts-rs bindings, Tauri 2 core (asset
protocol, dialog plugin, child processes), the bundled FFmpeg (LGPL, BtbN build), Svelte 5 + vitest/jsdom.

**Spec:** `docs/superpowers/specs/2026-10-22-clips-design.md` (approved 2026-10-22, binding: read it in full). It is
built on the media store (`2026-10-22-reactions-emoji-design.md` §5), the quotes replies panel
(`2026-10-22-quotes-design.md` §3.6) and their shipped code. Where the spec is silent or the code forces a choice,
**Spec reconciliation** below decides. Every item there is a **My call**, listed again in the hand-off report.

## Spec reconciliation (My calls)

1. **Protocol v3, forced update.** A v2 client's `Ready` fails to parse once a channel has kind `clips`, and it would
   hang on "connecting". So `PROTOCOL_VERSION` and `MIN_CLIENT_VERSION` both become `3`, and older builds get the
   existing "update required" screen. Quotes did the same.
2. **A clip's video in the media store.** It is a `media` row with `kind = 'clip'`, `location = 'r2'`,
   `content_type = 'video/mp4'`, `frames = 0` and `hash` = a **server-assigned random 64-hex key** (32 random bytes).
   It is not a content hash (spec §5), but it has the same shape, so `valid_hash` and every check that relies on
   it still hold. The R2 object key is `clips/<key>.mp4`. `MediaKind::location()` is the per-kind setting:
   `Clip → R2`, everything else `Disk`. Media cleanup only ever touches `location = 'disk'` rows.
3. **Thumbnails on the server disk** (spec §8 leaves this to the builder). The client makes a JPEG of at most 640 px
   on the long side, `POST /media/clip-thumb` turns it into WebP with the existing `process::quote_image`, and it is
   stored as `kind = 'clip_thumb'`. It is served, cached, backed up and cleaned up like emoji (cleanup keeps
   `clips.thumb_hash`).
4. **Pending uploads.** Only the poster's client shows them (spec §6 allows this). The server keeps an invisible
   `clip_uploads` ticket row that records the key, size and owner. Confirm checks against it, and a sweeper deletes
   tickets and their objects after 24 h.
5. **Rate limit of 20 per hour.** This is a database count, not an in-memory bucket, so it survives restarts and
   can't be dodged by abandoning uploads. A ticket is refused (429) when the clips you posted in the last rolling
   hour (deleted ones included) plus your open tickets from that hour reach 20. Cancel deletes the ticket, and Retry
   cancels the old ticket before it asks for a new one.
6. **Limits as enforced.** Size: 1 B to 200 MiB (`200 * 1024 * 1024`; re-derived 2026-10-28 when the Original
   preset was dropped: Sharp's hard ceiling is its 12 Mbps `-maxrate` + 160 kbps audio over 90.5 s ≈ 138 MB, and
   200 MiB ≈ 210 MB leaves about 50% headroom for VBV overshoot and MP4 overhead, shown to people as "200 MB"). The size is signed into the upload URL as
   `content-length`, and confirm re-checks it with a HEAD. Duration: the client keeps ≤ 90 000 ms. The ticket
   refuses more than 90 000 ms, and confirm accepts up to **90 500 ms**, because the encoder and AAC padding round
   up. Width and height must be 16 to 7680. The server can't decode the video, so duration and dimensions are the
   client's report (spec §5: "against the uploaded metadata").
7. **The S3 client.** The server uses `rusty-s3` (sans-IO SigV4 presigning, BSD-2-Clause, and its dependencies are
   already in `Cargo.lock`) to sign PUT, GET, HEAD and DELETE URLs. It runs HEAD and DELETE itself with `reqwest`,
   which becomes a normal dependency with `rustls-tls`. The client uploads with its existing `reqwest` plus the
   `stream` feature. R2 uses path style, region `auto`, and endpoint `https://<account>.r2.cloudflarestorage.com`.
8. **The R2 stand-in for development and tests (the choice asked for):** **an in-process fake S3 written in Rust**,
   in `server/src/testing/fake_s3.rs` behind the existing `testing` feature. It has its own independent SigV4
   verifier (it does not reuse `rusty-s3`, so it cross-checks the signer) and in-memory or on-disk objects. It
   handles PUT, GET (with `Range`), HEAD and DELETE. One implementation serves three users. Server integration tests
   (`testing::spawn` starts one per app, as tests start the fake LiveKit), client core tests (they already depend on
   `pulse-server/testing`) and `just dev-s3` for `just dev-server`/`dev-client` runs, through an example binary. No
   MinIO: it would add Docker and a third-party image to CI and to `cargo test`, it would test nothing the fake
   doesn't (Pulse uses four presigned verbs, no SDK), and quirks of real R2 can only be caught against real R2
   anyway. That is `pulse-app-server clips-check` (`just clips-check`), which the owner runs in the deploy task.
9. **Clips storage is optional per instance.** With the clip R2 variables unset, the ticket route answers 503 "Clips
   storage isn't set up on this server." and the rest of Pulse is unaffected. `deploy.sh` refuses a
   half-filled set.
10. **Cost shown in Server settings** = that server's clip GB × **$0.015/GB-month** (R2's Standard list price),
    ignoring the 10 GB free tier. Applying the free tier would need the all-servers total and so would leak it
    (spec §5). The copy says "at R2's list price". `just clips-storage` shows the real total with the free tier, and
    notes that the backups bucket shares the same free tier.
11. **Game names.** The registry key is `name_key` (reused from `quotes::name_key`: Unicode lowercase, trimmed,
    whitespace collapsed), unique per server. The spec writes `lower(name)`, but SQLite's `lower` is ASCII only.
    Names are 1 to 40 characters, with a cap of 300 per server. Games are never deleted in phase 1.
12. **Game guess.** It uses the folder (unless it is generic: `desktop`, `videos`, `downloads`, `documents`,
    `pictures`, `captures`, `clips`, `replays`, `recordings`, `nvidia`, `shadowplay`, `temp`, `tmp`, or a drive root),
    then the Title tag (unless it equals the file stem), then the file name **only when it matches NVIDIA's pattern**
    `<game> YYYY.MM.DD - HH.MM.SS.cc[.DVR]`, so `VID 20260101.mp4` is never "guessed".
13. **ffmpeg.** The build is BtbN's FFmpeg-Builds **`win64-lgpl-shared`** from the **FFmpeg 8.0 release branch**,
    pinned to one dated autobuild tag and its SHA-256. `scripts/fetch-ffmpeg.sh` fetches and verifies it (CI and
    `just fetch-ffmpeg`), and `client/src-tauri/tauri.windows.conf.json` bundles it as resources, so Linux builds
    never need it. Shared rather than static means `ffmpeg.exe` and `ffprobe.exe` share one set of DLLs. Expected
    size: about 100 to 150 MB installed and **about 35 to 50 MB more installer** (LZMA). Task 11 measures and
    records the real numbers. If BtbN prunes the pinned tag, the release build fails until it is re-pinned
    (build-time only).
14. **Encoders.** The order tried is `h264_nvenc` → `h264_amf` → `h264_qsv` → `h264_mf` (Windows' own encoder,
    software) → `libopenh264` → `libx264`. The LGPL build has no x264, so it only matters on dev machines with a
    system ffmpeg. The next encoder is tried **only when ffmpeg fails before reporting any progress** (an init
    failure such as no NVIDIA GPU or a busy NVENC). A failure mid-encode fails the job (Retry). The working encoder
    is remembered for the rest of the run. Decoding is on the CPU.
15. **Audio.** Two or more audio streams (NVIDIA's "separate mic track") are mixed with `amix=normalize=0`. No audio
    stream means no audio in the output. Metadata is stripped (`-map_metadata -1`: the Title tag, recorder tags).
16. **Presets** (spec §3.3 "my calls", made exact). The **short side** is capped, so portrait clips are right. Sizes
    are never upscaled and always even. fps is capped at 60.

    | Preset | Short side | fps | Video `-b:v` / `-maxrate` / `-bufsize` |
    |---|---|---|---|
    | Light (default) | ≤ 720 | ≤ 60 | 4M / 6M / 8M |
    | Sharp | ≤ 1080 | ≤ 60 | 8M / 12M / 16M |

    Audio: `-c:a aac -b:a 160k -ac 2 -ar 48000`. Size estimate = `(video_bps + 160_000) × kept_ms / 8000 × 1.02`
    bytes. At 1:30, Sharp's estimate is about 94 MB and its `-maxrate` ceiling about 138 MB, under 200 MiB. The
    client still checks the output size before uploading. **Owner's change (2026-10-28): there is no "Original"
    preset.** Sharp (1080p60) is the highest quality offered.
17. **Thumbnail** = the frame at kept time 1.0 s, or at half the kept time if that is under 2 s, taken from the
    original. **Filmstrip** = one JPEG sprite of **24 tiles, 72 px tall**, from keyframes only (`-skip_frame nokey`),
    so a 1.3 GB replay costs one read and no full decode.
18. **Preview.** The editor plays the local file through Tauri's **asset protocol**, with a per-file runtime scope
    (`asset_protocol_scope().allow_file`) and no static scope. A pure `preview_plan(probe, extension)` picks one of:
    - **Direct:** MP4/MOV with H.264 and AAC/MP3/no audio, or `.webm` with VP8/VP9.
    - **Remux:** H.264 in another container, with video copied and audio made AAC unless it already is.
    - **Encode:** everything else, at 540p with a 2.5 Mbps, fastest encoder preset.

    If the `<video>` element errors on a Direct file, the UI asks for Encode.
19. **CSP.** `media-src` gains `asset: http://asset.localhost https://*.r2.cloudflarestorage.com` and `img-src` gains
    `asset: http://asset.localhost`. The dev config also allows the fake S3 at `http://127.0.0.1:7895`. No account
    id goes in the repo.
20. **Fullscreen.** The window is frameless, so element fullscreen alone only fills the window. On
    `fullscreenchange` the UI also calls a core command that sets the window's fullscreen state.
21. **"Only on-screen items are drawn"** is done with `content-visibility: auto` cards, lazy thumbnails, and **one**
    mounted `<video>` (the playing clip), not a virtual list. Feeds are capped by paging (30) like history.
22. **Feeds.** Both views read one route, `GET /channels/{id}/clips` (newest first, `before` cursor, optional
    `game`/`author` filters, 30 per page). The list view renders it bottom-up. Chips come from `GET
    /channels/{id}/clips/facets`. The text-channel history machinery is not reused. `TextChannel.svelte` is
    untouched.
23. **Deleting a clip** soft-deletes the message, deletes the `clips` row and the reaction rows, and soft-deletes its
    replies (the quotes path, now shared). The R2 object is deleted right after commit, and the sweeper (every 10
    min) retries anything left. A deleted clip disappears from both views (no placeholder).
24. **Caption** is the message content: trimmed, 0 to 300 characters, rendered like message text, and @mentions are
    not resolved (a caption never pings).
25. **Development on Linux.** Release Linux builds never send (spec non-goal). Debug builds honour
    `PULSE_DEV_FFMPEG_DIR` (a folder with `ffmpeg` and `ffprobe`), so the editor can be exercised with `just
    dev-client` on the owner's Linux machine.
26. **Jobs.** Jobs are saved per account under the app's local data folder. Signing out cancels and deletes them.
    After a restart, a job that was preparing or uploading shows "Upload failed — Retry". One file per drop: the
    first video is used.
27. **TTLs.** Upload URL 1 h, play URL 1 h (asked for again on every play), ticket 24 h.
28. **Clips channels count unread and play the message sound like text channels.** `reaction_mode = 'normal'`, any
    number of reactions per person (spec §4.1).

## Review Focus

1. **The upload breaks or the app closes mid-send, then Retry.** The card shows "Upload failed — Retry". Retry
   finishes with exactly one posted clip (no duplicate even when the confirm response was lost) and leaves no
   orphan object for longer than the sweep. Pinned in Task 14 (`a_lost_confirm_response_never_double_posts`,
   `restart_turns_live_jobs_into_failed`) and Task 6 (`expired_tickets_and_orphans_are_swept`).
2. **A replay with two audio tracks (separate mic) or none.** The mic is mixed in, a silent file exports silent,
   and neither fails. Pinned in Task 13 (`two_audio_tracks_are_mixed`, `no_audio_maps_no_audio`).
3. **Portrait, rotated or odd-sized video** (a phone's 1080×1920 or rotate=90, a 1366×768 window capture). Never
   upscaled, even dimensions, the short side capped, displayed upright. Pinned in Task 12
   (`rotated_phone_video_is_portrait`) and Task 13 (`portrait_caps_the_short_side`, `odd_sizes_round_to_even`).
4. **Dropping everything, keeping under a second, or cutting at an edge.** No zero-length pieces, Send disabled with
   a reason, and Undo restores. Pinned in Task 16 (`dropping_everything_disables_send`,
   `cuts_too_close_to_an_edge_are_ignored`).
5. **An old clip, a deleted clip or a stranger asking to play.** Links are minted at play time and only for members
   of the clip's server. A deleted clip's link is 404, and an expired or tampered signature is refused by storage.
   Pinned in Task 8 (`play_urls_are_fresh_and_member_only`) and Task 2 (`expired_or_tampered_signatures_are_refused`).

## Task 2: The fake S3 (tests and dev)

**Files:**
- Create: `server/src/testing/fake_s3.rs` (move `server/src/testing.rs` to `server/src/testing/mod.rs`),
  `server/examples/fake_s3.rs`
- Modify: `server/Cargo.toml` (`hmac` optional in `testing`; `[[example]] name = "fake-s3" required-features =
  ["testing"]`), `justfile` (`dev-s3`)

**Interfaces:**
- Produces: `FakeS3::start(store: FakeStore) -> FakeS3` (binds `127.0.0.1:0`) and `FakeS3::start_on(addr, store)`.
  `FakeStore::Memory | FakeStore::Dir(PathBuf)`. `FakeS3::endpoint() -> String`. Consts `FAKE_BUCKET =
  "pulse-clips-test"`, `FAKE_KEY_ID`, `FAKE_SECRET` (obvious test strings). `FakeS3::object(key) -> Option<(Vec<u8>,
  String /*content-type*/)>`, `FakeS3::put_raw(key, bytes)`, `FakeS3::keys() -> Vec<String>`,
  `FakeS3::requests() -> Vec<(Method, String)>`,
  `FakeS3::set_down(bool)` (answers 503 to everything while down; tests use it for broken storage).
- Behaviour: path-style `/{bucket}/{key}`. Every request must carry a valid **SigV4 query presign**
  (`X-Amz-Algorithm=AWS4-HMAC-SHA256`, a credential with the fake's key id and region `auto`, service `s3`,
  `X-Amz-Date` + `X-Amz-Expires` not elapsed, and `X-Amz-Signature` matching a canonical request rebuilt from the
  incoming method, path, query and **signed headers**, with payload `UNSIGNED-PAYLOAD`). Otherwise it answers 403
  with an S3-style XML error. Verbs: PUT stores the body and content type and answers 200. GET answers 200, or 206
  for `Range: bytes=a-b` / `a-`, with `Accept-Ranges: bytes` and `Content-Type`. HEAD gives `Content-Length`, or 404.
  DELETE answers 204 (also for a missing key, like S3). The verifier is written independently of `rusty-s3` with
  `hmac` + `sha2`.
- Wiring it into `testing::spawn` is Task 3's job (it needs `Config.clips`).

- [ ] **Step 1: failing tests** (unit, in `fake_s3.rs`):
  - `verifier_accepts_the_aws_documented_example`: AWS's published presigned-URL example (S3 docs, "Authenticating
    Requests: Using Query Parameters": `examplebucket`, `test.txt`, `AKIAIOSFODNN7EXAMPLE`, 20130524T000000Z, 86400 s,
    region `us-east-1`) verifies with the documented signature, at a fixed "now".
  - `expired_or_tampered_signatures_are_refused`: a URL presigned with `rusty-s3` (dev-dependency use only) works,
    then fails with 403 once expired (fixed clock), when one query character is flipped, and for a different key.
  - `a_put_must_match_its_signed_length`: a PUT URL that signs `content-length: 5`, sent with 6 bytes → 403, nothing
    stored. With 5 bytes → 200, `object()` returns them with the signed content type.
