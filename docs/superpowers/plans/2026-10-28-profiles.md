# Profiles (cards, avatars, banners, name styles): implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** profile cards (a quick card and a full profile) with an avatar and banner (animated allowed), a two-colour
card theme with a glowing edge, pronouns and a bio, and a name font and colour that show everywhere the name is
drawn. They are edited in Settings → Profile with a live preview, and nothing changes until Save.

**Architecture:** the profile is stored as new columns on `users`. Migration 0010 adds them and drops the unused
`images` table. The name style (font and colours) and the avatar's still frame travel inside `User`, so every list,
message and member row can draw a name without asking for more. The card's own fields (banner, theme, pronouns,
bio), the stats, the badges and the Name Archive come from one `GET /users/{id}/profile`. Avatars and banners are
two new media kinds on the existing disk media store. They share the emoji/quote pipeline, with a crop rectangle
applied to every frame. Saving is one `PUT /me/profile`, which validates everything, lightens name colours on the
server and publishes `ProfileUpdated` to everyone (the same audience as presence). On the client, one name-style
resolver (font, colour, optional role colour, the "Show name styles" setting) feeds a `Name` component, and one
`Avatar` component does still-or-animated. Every place that draws a person uses these two.

**Tech Stack:** Rust (axum, sqlx/SQLite, `image`, `webp-animation`), ts-rs bindings, Tauri 2 core, Svelte 5 +
vitest/jsdom, `@fontsource/*` packages for the bundled name fonts.

**Spec:** `docs/superpowers/specs/2026-10-22-profiles-design.md` (approved; binding, read it in full). It is built
on the media store (`2026-10-22-reactions-emoji-design.md` §5) as shipped, and on the clips branch as merged (read
`docs/superpowers/plans/2026-10-28-clips.md` for migration 0009, protocol v3 and the media store's R2 location).
Where the spec is silent or the code forces a choice, **Spec reconciliation** below decides. The owner approved
the design and asked for the push to be built without reviewing this plan, so every open point is decided here,
marked **My call**, and comes with what it costs if it turns out wrong.

## Spec reconciliation (My calls)

1. **No protocol bump: stays v3 (My call).** Every addition is backward compatible. The new `User` fields are
   `#[serde(default)]` and serde ignores unknown fields, so a v3 build reads the new `Ready`, `Member`, `Person` and
   `UserCreated` without trouble. The new `ProfileUpdated` event is skipped by an old core, which drops frames it
   can't parse (`client/src-tauri/src/gateway.rs`: `Err(_) => continue`). An old build just shows plain names and
   initials until it updates. `PROTOCOL_VERSION` and `MIN_CLIENT_VERSION` stay `3`. Task 1 pins this with a test.
   *If wrong:* an old build would hang on "connecting". The fix is a one-line bump of both constants to 4 and a new
   installer.
2. **Storage: columns on `users`, not a `profiles` table (My call).** The spec allows either, and every read that
   needs the style already reads `users`. The new columns are `banner_hash`, `theme_top`, `theme_bottom` (both
   `NOT NULL`, defaulting to Plain), `name_font`, `name_color` (`"#rrggbb"` or `"#rrggbb,#rrggbb"`), `pronouns` and
   `bio`. `avatar_hash` is reused. There are no foreign keys to `media` (the existing `avatar_hash` column can't
   gain one in SQLite without a rebuild), so Save checks that the hashes exist instead. The unused `images` table
   from 0001 is dropped (spec §5). *If wrong:* a later move to a table is one migration.
3. **The avatar still travels in `User` (My call).** `User` gains `avatar_still: Option<String>` (the media row's
   `still_hash`, set only for an animated avatar) and `style: NameStyle`. Lists need the still without asking for
   it separately. The banner and its still are in `CardProfile` only. *If wrong:* about 70 bytes more per person in
   `Ready`.
4. **Avatar and banner processing (spec §4.2, made exact).** There are two new kinds, `avatar` and `banner`, both
   `location = 'disk'`. Inputs are PNG, JPEG, GIF or WebP, **8 MB** at most, at most 4096 px a side (the existing
   decode limit), and at most **200 frames**. The 100 Mpx animation decode budget and `MAX_ALLOC` are shared with
   emoji. A crop rectangle in source pixels (optional) is applied to every frame. Then each frame is fitted by
   "cover": centre-cropped to the target aspect and resized to exactly the target size (small sources are
   enlarged). Outputs:

   | Kind | Still | Animated | Still cap | Animated cap | Fitted-pixel budget |
   |---|---|---|---|---|---|
   | avatar | 256×256 | 256×256 | 512 KB | **1 MB** | 32 Mpx |
   | banner | 960×384 | **600×240** | 1 MB | **2 MB** | 32 Mpx |

   An animated banner is 600×240 rather than 960×384 (My call). All fitted frames are held until encoding, and 200
   frames at 960×384 would be about 295 MB of RGBA. 600×240 is the size people's Discord banner GIFs already are,
   and the card shows the banner at about 300×104. *If wrong:* animated banners are slightly soft on the full
   profile at 2× scaling, and raising it is a constant. Every animated upload gets its first-frame still, as emoji
   already do.
5. **The crop is done on the server (My call).** An animated GIF can't be cropped in the webview without decoding
   it. The UI sends the rectangle as query parameters (`?x=&y=&w=&h=`, all or none). The server refuses a
   rectangle outside the image's logical size (400 "The crop is outside the image."). With no rectangle, the server
   centre-crops. *If wrong:* nothing visible changes; a client-side crop could be added later.
6. **Staging (spec §4.1) needs nothing new on the server.** An upload is a `media` row like any other. Cleanup
   already removes rows nothing uses after the 24 h grace (`spawn_cleanup`), which is the spec's 24 hours. Cleanup
   gains `users.avatar_hash` and `users.banner_hash` as "in use", and their stills follow. Save refuses a hash that
   has no `media` row of the right kind (400 "That picture has expired. Upload it again."). The current value is
   always accepted.
7. **Name colours: one rule, on both sides (My call; spec §4.5).** A colour is accepted as `#rrggbb`
   (case-insensitive and stored lowercase). If its WCAG relative luminance is **under 0.39**, it is mixed towards
   white in steps of 1% until it reaches 0.39 (`c' = floor(c + (255 − c)·k/100 + 0.5)` per channel, for the
   smallest such k). 0.39 is the highest threshold that every approved preset passes **unchanged** (the darkest is
   the Sunset gradient's `#ff7fae` at 0.395). It gives at least 5.1:1 on `--bg-4` (`#34363d`), the lightest surface
   a name sits on in the app, and at least 3:1 (large text) on the worst card surface (rule 8). The same rule runs
   in Rust (Save) and TypeScript (the preview), with shared test vectors. The rule applies to **every** name colour,
   presets included. Presets come out unchanged, so it only matters for custom colours. *If wrong:* custom colours
   look paler than wanted. The threshold is one constant on each side.
8. **Card readability (spec §4.3, exact).** The card surface is each theme colour mixed **30%** into near-black
   `#0d0e12`, as a gradient from top to bottom. The mockup said "about 35%". At 35% a pure white theme leaves
   secondary text under 4.5:1. Panels (the bio and info box, the Board cards) use **18%**. Card text uses fixed
   colours, `--card-text: #f2f3f6` and `--card-text-2: #d6d8df`. On the worst themes (white, yellow, cyan, green),
   the surface gives ≥ 6.5:1 and ≥ 5.1:1 and panels ≥ 8:1. The name (20 px bold, so large text) is ≥ 3.08:1. The
   border is 1.5 px, a gradient of the raw theme colours, with a glow (`box-shadow` of each colour at 45% alpha,
   22 px blur). It is static, so reduced motion changes nothing. A custom pair is accepted as is (spec).
9. **The eight fonts (spec §4.4: the mockup's set kept).** They come from the `@fontsource/*` npm packages, at
   **exact** version `5.3.0` (released 2026-07-19), all **OFL-1.1**. Each ships one weight, and only the latin and
   latin-ext woff2 subsets, in a new `nameFonts.css` (the same pattern as `fonts.css` for Onest). The browser only
   downloads a face when a name uses it. About 285 KB are added to the bundle.

   | key | Picker label | Family | Weight | Scale | Subsets |
   |---|---|---|---|---|---|
   | `cormorant-garamond` | Elegant | Cormorant Garamond | 600 | 1.15 | latin, latin-ext |
   | `fredoka` | Rounded | Fredoka | 500 | 1.00 | latin, latin-ext |
   | `press-start-2p` | Pixel | Press Start 2P | 400 | 0.68 | latin, latin-ext |
   | `pacifico` | Script | Pacifico | 400 | 0.95 | latin, latin-ext |
   | `caveat` | Handwritten | Caveat | 600 | 1.20 | latin, latin-ext |
   | `space-grotesk` | Grotesque | Space Grotesk | 600 | 1.00 | latin, latin-ext |
   | `bricolage-grotesque` | Quirky | Bricolage Grotesque | 600 | 1.00 | latin, latin-ext |
   | `orbitron` | Techy | Orbitron | 600 | 0.86 | latin (it has no latin-ext) |

   "Default" (`null`) is the app font. The **scale** is the per-font size factor from spec §3.3, so a name lines
   up with others. The values are starting points by eye. Task 15's checklist (item
   6) asks the owner to judge them, and the builder does not retune them by eye. Glyphs a face lacks fall back to
   Onest. *If wrong:* a font looks a little big or small; each scale is one number in
   `lib/nameFonts.ts`.
10. **Where the name style shows (spec §3.3, made exact; My call on the edges).** The style shows wherever a
    person's name is drawn as a label:
    - chat message authors and "replying to" names;
    - the member list, voice occupants in the channel list and voice tiles;
    - the DM/conversation list and DM headers, group members;
    - the people board and picker;
    - quote authors and member-linked quote speakers;
    - the @ autocomplete;
    - mention pills (font and colour on the text, the pill background kept);
    - clip cards (once clips is in).

    Names inside sentences stay plain: typing ("alex is typing"), tooltips, aria labels, "added by", system lines,
    "Watching: …". *If wrong:* each further site is one `Name` swap.
11. **The role rule is client-side only (spec §3.3).** `resolveNameStyle(user, { roleColor, showStyles })`. A role
    colour replaces the colour (solid or gradient) and keeps the font. It goes through the same lightening (My
    call: "no combination can be unreadable" covers roles too). `AppState.roleColors[serverId][userId]` is the
    input, always empty in this push. The roles push fills it.
12. **"Show name styles" (spec §3.3).** It is under Settings → **Appearance** (a new section), on by default, and
    kept per device in `localStorage` like "Animate emoji". Off means the default font and colour for everyone.
    Role colours **still show** (My call: they are server information, not a personal style). Avatars and banners
    are unaffected. *If wrong:* one condition in the resolver.
13. **Motion (spec §3.4, exact).** On the quick card and full profile, avatars and banners animate whenever the
    window is focused and the card is on screen. In lists (chat, member list, voice occupants, voice tiles,
    conversation list, people board/picker, quote items), they show the still and animate only while the pointer
    is over that avatar or its name row. Reduced motion means the still everywhere. Going live freezes them too,
    as for emoji. The "Animate emoji" setting does **not** apply (My call: it is about emoji). This reuses
    `wireEmoji`'s machinery: `lib/animate.svelte.ts` gains `wireAnimated(img, anim, still, decide)`, and
    `wireEmoji` becomes `wireAnimated` with the emoji rule, unchanged in behaviour.
14. **Opening the card.** Clicking a styled name or an avatar in chat, the member list, the conversation list,
    mentions, quote items or the people board opens the quick card. Clicking a voice tile or a voice occupant
    already opens the participant menu, so that menu gains **"View profile"** as its first item, and the tile's
    name text opens the card directly (My call). *If wrong:* one extra click from voice.
15. **The full profile is a modal (spec §7: the builder's choice).** It is centred, like Settings, at about 880×600.
    The card is on the left at 340 px wide. On the right are Board panels: **Stats**, **Name Archive** and
    **Trophy case**. Stats always shows: voice hours, member since, most-used reaction (hidden if none) and times
    renamed (hidden if 0). The Name Archive is hidden while there are no rows (nickname renaming isn't built, so
    for now it never shows). **The trophy case always shows**, with an empty state, "No trophies yet", because the
    hand-off asked for one. This departs from spec §3.2 "hidden, not shown empty" for this one panel only (My
    call). *If wrong:* it is one `{#if}`.
16. **Stats, exact.**
    - **Voice:** `voice_seconds` = Σ over the user's `voice_sessions` of `(left_at, or now if still open) −
      joined_at`. That table only ever records server voice channels.
    - **Member since:** `users.created_at`.
    - **Most-used reaction** (`top_reaction`): the emoji the user reacted with most, counted on messages that
      aren't deleted, ties going to the most recent. It is `custom:<id>` for a custom emoji.
    - **Times renamed:** the count of `nickname_history` rows targeting them.
    - **Name Archive:** those rows' `new_nick` values, newest first, with the server and who renamed them.

    These are totals across all servers, the same everywhere (spec). Voice is shown as "N min" under an hour, one
    decimal under 10 h ("2.5 h"), then whole hours ("143 h").
17. **Badges.** `user_badges` exists (0001) but nothing writes it. The profile returns its rows as `Badge { key,
    earned_at, first_earner }`. The UI looks keys up in `lib/badges.ts` (`BADGES`, empty in this push). An unknown
    key shows the key in title case with the trophy icon. The quick card's badge row is hidden when empty.
18. **Text limits (spec §4.6, exact).**
    - **Pronouns:** trimmed, 0 to 40 characters (`chars()`), with no control characters; empty is stored as NULL.
    - **Bio:** `\r\n` becomes `\n`, trailing whitespace is trimmed, 0 to 190 characters, at most 4 `\n`, no other
      control characters; empty is NULL.

    The bio is rendered with the message renderer (`renderMarkdown(bio, [], customEmoji)`: markdown, standard and
    custom emoji, no mentions) and edited in `EmojiBox`, so custom emoji work. A custom emoji token counts as its
    stored characters (My call). *If wrong:* an emoji-heavy bio reaches 190 sooner.
19. **The quick card's message box.** Enter sends to your DM with them. It is created if needed (`createDm`),
    queued through the existing outbox (`sendMessage`), and then the app switches to that DM and closes the card
    (My call). It is hidden on your own card.
20. **The editor (spec §4.1).** Settings → **Profile** (a new first section). Leaving with unsaved changes asks
    first. That covers closing Settings, switching section, Escape and the backdrop: "Discard your profile
    changes?" with "Keep editing" and "Discard". Reset returns the draft to the saved profile. Save sends one `PUT
    /me/profile`, and on success the draft takes the server's answer (lightened colours included). A failed Save
    keeps the draft and shows the server's message.
21. **Validation statuses.** 400 for bad input, 404 for an unknown user, 429 for rate limits. `PUT /me/profile`
    first hits `s.limits.mutate_user` and calls `crate::media::writes_ok(&s.cfg)?`. Avatar and banner uploads share
    `upload_user` (30 an hour), the processing slots and the disk guard with emoji.

## Review Focus

1. **Leaving the editor with something staged** (an avatar uploaded, a colour picked) through Escape, the backdrop,
   the close button or another section. People expect a question first, and after "Discard" nobody (including
   their own chat line) ever sees the staged picture. Pinned in Task 14 (`every way out asks when dirty`,
   `discard leaves the saved profile untouched`).
2. **A real-world upload that is too much:** a 9 MB phone photo, a 250-frame GIF, a 6000 px panorama, a PDF
   renamed `.png`, or a crop dragged off the edge. Each should get a clear message in the editor and leave the
   draft as it was. Pinned in Task 2 (`profile_uploads_refuse_what_they_should`, `a_crop_outside_the_image_is_refused`)
   and Task 14 (`a refused upload keeps the draft and shows the message`).
3. **Someone changes their profile while you are looking at them:** their name in already-rendered messages, the
   member list, an open quick card and the full profile all update live, with no refetch storm. Pinned in Task 8
   (`ProfileUpdated updates people, members, me and a cached profile`) and Task 11 (`an open card follows a
   ProfileUpdated`).
4. **Ugly choices:** a black or pure blue custom name, a white or yellow custom theme. The name is lightened
   identically in the preview and after Save, and card text keeps its contrast. Pinned in Task 4
   (`lighten_matches_the_shared_vectors`) and Task 7 (`lighten matches the shared vectors`, `worst themes keep text
   readable`).
5. **A busy channel full of animated avatars:** only stills in lists, one animates under the pointer, none under
   reduced motion, and the card animates. Pinned in Task 9 (`lists show the still and animate on hover`, `reduced
   motion never animates`, `cards animate`).
6. **A staged upload swept before Save** (someone leaves the editor open over a day). Save says the picture
   expired, and nothing half-saves. Pinned in Task 4 (`a_swept_upload_is_refused_on_save`).
