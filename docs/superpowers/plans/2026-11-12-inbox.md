# Inbox (#306) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** one place for everything meant for you, across every server, DM and group: @mentions and replies to your
messages, with tabs All / Mentions, an unread badge on a top-bar button, jump-to-message, read state that follows
your read points, and live updates on every device.

**Spec:** `docs/superpowers/specs/2026-11-12-inbox-design.md`

**Tech Stack:** Rust (axum, sqlx/SQLite, ts-rs), Tauri 2 core (reqwest), Svelte 5 + vitest.

**Status: done (2026-11-12).** As built, two changes to the plan below: the hub remembers the count each connected
user was last told (Ready, then inbox events), so a read point, seen point or mute that doesn't change the count sends
nothing (and users with no connection get no inbox work at all); and a mute or unmute makes the client fetch its lists
again. Deferred: #324 (a clip reply opens its clip's panel; since built), #325 (a timed mute running out updates the count; since
fixed by a server sweep), #326
(thread replies you're part of, which the app doesn't alert on today).

## What the app already has (reused, not rebuilt)

- **Mentions are already per-you rows.** `mentions (message_id, user_id)` holds every typed `@name` resolved to people
  who can see the chat, *and* (since threads landed) the author of the message a reply answers ("a reply pings whoever
  it replies to", `messages::routes::send`). So the inbox's items are exactly the user's mention rows: mentions in the
  main list and in quote/clip threads, and replies. The app has no @everyone/@here or role mentions, so there is
  nothing more to derive.
- **Read points** (`read_states`, `reads::advance`, #111 read-all) and **thread seen points** (`thread_reads`,
  `threads::mark_seen`) already decide when a mention badge clears. An inbox item counts as read by the same rule
  (main list: `id <= last_read_message_id`; reply: `id <= last_seen_id`), so reading the message in its channel reads
  the item, with no new write on those paths.
- **Mutes** (`notification_prefs.muted`, #131/#195): mention badges ignore mutes; the spec says muted chats add no
  items unless it's an explicit @mention. Only reply-only items are hidden by an active mute (channel or its server).
- **Jump** (`lib/jump.ts`) and the replies panel request (`ui.openReplies`, as a notification click does).
- **Popover and list styles:** `PinsPopover.svelte` (`menu-surface pop-in`, rows with author / one-line preview /
  note), `Segmented.svelte` for the tabs, the top bar's `.win` buttons (patch notes, report a bug).
- **Quick actions** registry (`lib/quickActions.ts`, #309).

## Builder's calls (with why)

- **Explicit vs reply.** A new `mentions.explicit` column (1 = typed `@name`, 0 = only the reply's ping). The send path
  knows which; the backfill marks existing rows 0 where the message replies to that user's message and its text has no
  `@<their username>` (a username prefix, e.g. `@sam` in `@samuel`, reads as explicit: old rows only, harmless).
  Mentions tab = `explicit = 1`; All = every row. An item that is both is a Mention (and still shows the reply snippet).
- **Read state = derived + two small tables**, not a row per item: an item is read when (a) its read point / seen point
  covers it, (b) `inbox_reads (user_id, message_id)` has it (you jumped to it), or (c) it is at or before
  `inbox_cleared.upto` (Mark all read). Mark all read is O(1) (one marker) and new items after it are unread;
  per-item rows exist only for items opened from the inbox, and the hygiene sweep prunes rows older than 30 days.
- **30 days by id:** items are `mentions.message_id >= MessageId::floor(now - 30 d)` on a new
  `mentions (user_id, message_id)` index (replacing `mentions_user (user_id)`, a prefix of it), newest first,
  pages of 30 (`before` cursor).
- **Visible items** follow the badges' rule: a channel you have a read point in, not in Recently deleted (nor its
  server), a DM/group you're still in, the message (and a reply's quote) not deleted.
- **Events, in the hub.** `Hub::publish` asks `inbox::follow_ups(db, &event)` for the inbox events an event implies
  and delivers them right after it, under the same `in_order` hold the trigger was published under, to the user's
  own sessions only. So every place that already announces a read point, a thread seen point, a delete or a mute
  keeps the inbox in step without touching each call site:
  - `MessageCreated` with mentions → `InboxItemAdded { user_id, item, unread }` per mentioned user whose item is
    visible (a muted reply-only one isn't).
  - `ReadStateUpdated` / `ThreadSeen` / `MutesChanged` → `InboxUpdated { user_id, unread, read: [], read_upto: None }`
    for that user (clients mark loaded items read from the read event itself).
  - `MessageDeleted` with mentions → `InboxUpdated { removed: [id] }` per mentioned user.
  - The inbox routes publish `InboxUpdated { read: [id] }` / `{ read_upto }` themselves.
  0.2.x clients ignore unknown events and the new optional Ready field.
- **Ready** carries `inbox_unread: Option<u32>` so the badge is right at start (optional: older servers send none).
- **Mute expiry** (a timed mute running out) and a server/channel being deleted change the count with no event to
  the user: the client refetches the count (`GET /inbox/unread`) on `ChannelDeleted`, `ServerDeleted`,
  `ChannelRemoved`, `ServerRestored`, `ChannelRestored` and when the popover opens. (#325, since: a sweep every
  15 s, `dms::sweep`, clears run-out mutes and publishes their owners' `MutesChanged`, so a mute running out
  recounts through the inbox worker like any other mute change, and clients fetch their lists again.)
- **Jump target:** a main-list item jumps with `jumpTo` (flash); a reply opens its quote's replies panel (as a
  notification click does); a clip, or a clip reply, opens that clip's panel (clips have no history to jump in; since
  #324, shared with search in `lib/openMessage.ts`). Either way the
  item is marked read (`POST /inbox/{message_id}/read`).
- **Tabs, not a toggle** (`Segmented`, as Settings uses), remembered per device in `localStorage`
  (`pulse.inbox.tab`).
- **Button:** a `.win` button left of Patch notes in the top bar, `inbox` icon at 16, a count pill like the Home tab's
  (`99+`). The popover drops from it on the right.
- **Quick switcher:** an "Inbox" action (keywords: mentions, replies, notifications), listed after `>` and under the
  places for `inb…`.

## Server

- [ ] **Migration `00NN_inbox.sql`** (next free at merge time; foreign keys are off at migration time, nothing is
  rebuilt): `ALTER TABLE mentions ADD COLUMN explicit INTEGER NOT NULL DEFAULT 1`; the backfill `UPDATE` above;
  `CREATE INDEX mentions_user_message ON mentions(user_id, message_id)`; `DROP INDEX mentions_user`;
  `CREATE TABLE inbox_reads (user_id → users ON DELETE CASCADE, message_id → messages ON DELETE CASCADE, PK both)`;
  `CREATE TABLE inbox_cleared (user_id PK → users ON DELETE CASCADE, upto TEXT NOT NULL)`.
- [ ] **Protocol:** `InboxKind { Mention, Reply }`, `InboxItem { message, kind, replied_to: Option<InboxSnippet>, read }`,
  `InboxSnippet { message_id, author_id, content, deleted }`, `InboxPage { items, unread }`, `InboxUnread { unread }`,
  `InboxReadAllRequest { upto: Option<MessageId> }`; events `InboxItemAdded`, `InboxUpdated` (`only_for` the user);
  `Ready.inbox_unread`. Regenerate the TS bindings.
- [ ] **Send path:** `mentions::store(.., explicit)`; `send` stores typed mentions as explicit and the reply ping not.
- [ ] **`server/src/inbox/`**: the shared SQL (visible items, read flag), `unread(db, me)`, `page(db, me, before,
  mentions_only)`, `item(db, me, message)`, `follow_ups(db, &event)`; routes `GET /inbox?before&mentions`,
  `GET /inbox/unread`, `POST /inbox/{message_id}/read`, `POST /inbox/read-all` (rate-limited `mutate_user`).
- [ ] **Hub:** deliver `follow_ups` after each published event.
- [ ] **Hygiene:** prune `inbox_reads` older than 30 days.
- [ ] **Tests (server/tests/inbox.rs):** mention + reply items, Mentions tab, others' / own excluded, read by read
  point, by thread seen, by jump, by mark all (and a later item stays unread), 30-day cut, paging, muted reply hidden
  but muted mention kept, deleted message/channel/left group hidden, events (added, read sync to a second session,
  removed on delete), Ready count, explicit backfill.
